# Лабораторная работа № 6

## Описание работы

В данной лабораторной работе выполняется создание и настройка объектов базы данных в Microsoft SQL Server с использованием языка SQL. Работа выполняется поэтапно с помощью отдельных SQL-скриптов.

Для изоляции объектов лабораторной работы от существующих баз данных была создана отдельная база данных `Lab6_DDL`. Все объекты, созданные в рамках заданий, размещаются в этой базе данных.

## Задание 1. Создание схемы и таблиц

### Цель задания

Создать отдельную базу данных, схему `lab6` и две таблицы — `Customer` и `Product` — с заданными типами данных, первичными ключами и ограничениями целостности.

### Ход выполнения

Работа была разделена на четыре этапа. Каждый этап сохранён в отдельном SQL-файле.

### Задание выполнено в директории `DBCourseLabs\lab06\task01`. 

#### 1. Создание базы данных — `01.sql`

Сначала была создана база данных `Lab6_DDL`. Для этого использовалась системная база данных `master`.

```sql
USE master;
GO

CREATE DATABASE Lab6_DDL;
GO
```

Создание отдельной базы данных позволяет выполнять лабораторную работу независимо от существующих баз и не изменять их таблицы.

#### 2. Создание схемы — `02.sql`

В созданной базе данных была создана схема `lab6`, предназначенная для размещения объектов лабораторной работы.

```sql
USE Lab6_DDL;
GO

CREATE SCHEMA lab6;
GO
```

Схема позволяет логически группировать таблицы и обращаться к ним с указанием имени схемы, например `lab6.Customer`.

#### 3. Создание таблицы клиентов — `03.sql`

В схеме `lab6` была создана таблица `Customer` со следующими столбцами:

| Столбец | Тип данных | Назначение |
|---|---|---|
| `CustomerID` | `INT` | Идентификатор клиента, первичный ключ |
| `Name` | `NVARCHAR(100)` | Имя клиента, обязательное поле |
| `City` | `NVARCHAR(50)` | Город клиента, обязательное поле |
| `Email` | `NVARCHAR(100)` | Электронная почта, необязательное поле |
| `CreatedAt` | `DATETIME2` | Дата и время создания записи |

Для таблицы были заданы следующие ограничения:

- `PK_Customer` — первичный ключ по столбцу `CustomerID`, обеспечивающий уникальную идентификацию клиентов.
- `UQ_Customer_Email` — ограничение уникальности для столбца `Email`.
- `DF_Customer_CreatedAt` — значение по умолчанию `SYSDATETIME()`, автоматически устанавливающее текущие дату и время, если значение `CreatedAt` не указано при добавлении записи.

Столбцы `Name` и `City`, а также `CustomerID` и `CreatedAt` объявлены обязательными с помощью `NOT NULL`. Столбец `Email` допускает отсутствие значения.

#### 4. Создание таблицы товаров — `04.sql`

В той же схеме была создана таблица `Product`.

| Столбец | Тип данных | Назначение |
|---|---|---|
| `ProductID` | `INT` | Идентификатор товара, первичный ключ |
| `Name` | `NVARCHAR(100)` | Название товара, обязательное поле |
| `Price` | `DECIMAL(10,2)` | Цена товара, обязательное поле |

Для таблицы были заданы следующие ограничения:

- `PK_Product` — первичный ключ по столбцу `ProductID`.
- `CK_Product_Price` — проверочное ограничение, запрещающее отрицательные значения цены с помощью условия `Price >= 0`.

Столбцы `ProductID`, `Name` и `Price` объявлены обязательными с помощью `NOT NULL`.

**#### 5. Создание таблицы заказов — `05.sql`**

В схеме `lab6` была создана таблица `Orders` для хранения информации о заказах клиентов.

| Столбец | Тип данных | Назначение |
|---|---|---|
| `OrderID` | `INT IDENTITY(1,1)` | Идентификатор заказа, автоматически нумеруемый первичный ключ |
| `OrderDate` | `DATE` | Дата заказа, обязательное поле |
| `CustomerID` | `INT` | Идентификатор клиента, обязательное поле |

Для таблицы были заданы следующие ограничения:

- `PK_Orders` — первичный ключ по столбцу `OrderID`.
- `DF_Orders_OrderDate` — значение по умолчанию, устанавливающее текущую дату, если дата заказа не указана.
- `FK_Orders_Customer` — внешний ключ на `lab6.Customer(CustomerID)`, обеспечивающий связь заказа с существующим клиентом.

Столбец `OrderID` использует свойство `IDENTITY(1,1)`, благодаря которому идентификаторы заказов генерируются автоматически, начиная с 1 с шагом 1. Столбцы `OrderDate` и `CustomerID` объявлены обязательными с помощью `NOT NULL`.

**#### 6. Создание таблицы позиций заказа — `06.sql`**

В схеме `lab6` была создана таблица `OrderLine` для хранения информации о товарах, включённых в заказы, и их количестве.

| Столбец | Тип данных | Назначение |
|---|---|---|
| `OrderID` | `INT` | Идентификатор заказа, обязательное поле |
| `ProductID` | `INT` | Идентификатор товара, обязательное поле |
| `Qty` | `INT` | Количество товара в заказе, обязательное поле |

Для таблицы были заданы следующие ограничения:

- `PK_OrderLine` — составной первичный ключ по столбцам `(OrderID, ProductID)`, обеспечивающий уникальность пары заказа и товара.
- `FK_OrderLine_Orders` — внешний ключ на `lab6.Orders(OrderID)` с каскадным удалением связанных позиций заказа с помощью `ON DELETE CASCADE`.
- `FK_OrderLine_Product` — внешний ключ на `lab6.Product(ProductID)`, обеспечивающий связь позиции с существующим товаром.
- `CK_OrderLine_Qty` — проверочное ограничение, запрещающее нулевое и отрицательное количество товара с помощью условия `Qty > 0`.

Все столбцы объявлены обязательными с помощью `NOT NULL`. Составной первичный ключ не позволяет добавить один и тот же товар в один заказ несколькими отдельными строками.


#### 7. Заполнение таблиц тестовыми данными и проверка ограничений — `insert.sql`

На этом этапе были добавлены тестовые данные для проверки созданных таблиц и ограничений.

В таблицу `lab6.Customer` добавлены три клиента, один из которых не имеет электронной почты. В таблицу `lab6.Product` добавлены три товара с положительными ценами. Затем созданы два заказа для разных клиентов и добавлены по две позиции в каждый заказ.

```sql
USE Lab6_DDL;
GO

-- Добавление трёх клиентов, у третьего Email не указан
INSERT INTO lab6.Customer (CustomerID, Name, City, Email)
VALUES
    (1, N'Иван Петров', N'Москва', N'ivan@example.com'),
    (2, N'Анна Смирнова', N'Казань', N'anna@example.com'),
    (3, N'Пётр Иванов', N'Самара', NULL);
GO

-- Добавление трёх товаров
INSERT INTO lab6.Product (ProductID, Name, Price)
VALUES
    (1, N'Ноутбук', 75000.00),
    (2, N'Мышь', 1500.00),
    (3, N'Клавиатура', 3500.00);
GO

-- Создание двух заказов
DECLARE @Order1 INT, @Order2 INT;

INSERT INTO lab6.Orders (CustomerID)
VALUES (1);

SET @Order1 = CONVERT(INT, SCOPE_IDENTITY());

INSERT INTO lab6.Orders (CustomerID)
VALUES (2);

SET @Order2 = CONVERT(INT, SCOPE_IDENTITY());

-- Добавление по две позиции в каждый заказ
INSERT INTO lab6.OrderLine (OrderID, ProductID, Qty)
VALUES
    (@Order1, 1, 1),
    (@Order1, 2, 2),
    (@Order2, 2, 1),
    (@Order2, 3, 1);
GO
```

Для проверки использовались следующие запросы:

```sql
USE Lab6_DDL;
GO

SELECT * FROM lab6.Customer;
SELECT * FROM lab6.Product;
SELECT * FROM lab6.Orders;
SELECT * FROM lab6.OrderLine;
GO
```

Запросы позволяют убедиться, что тестовые записи были успешно добавлены. Для проверки ограничений далее выполняются отдельные запросы с заведомо некорректными данными.

#### 8. Проверка ограничений — `check.sql` и последующие проверки

**Проверка 1. Добавление товара с отрицательной ценой**

```sql
USE Lab6_DDL;
GO

INSERT INTO lab6.Product (ProductID, Name, Price)
VALUES (99, N'Некорректный товар', -100.00);
GO
```

Ожидаемый результат: SQL Server отклоняет добавление товара из-за ограничения `CK_Product_Price`, которое требует, чтобы цена была неотрицательной.

Пример сообщения об ошибке:

```text
The INSERT statement conflicted with the CHECK constraint "CK_Product_Price".
```

**Проверка 2. Добавление позиции заказа с несуществующим ProductID**

```sql
USE Lab6_DDL;
GO

INSERT INTO lab6.OrderLine (OrderID, ProductID, Qty)
VALUES (1, 999, 1);
GO
```

Ожидаемый результат: SQL Server отклоняет добавление позиции из-за ограничения внешнего ключа `FK_OrderLine_Product`. Товар с идентификатором `999` отсутствует в таблице `lab6.Product`.

Пример сообщения об ошибке:

```text
The INSERT statement conflicted with the FOREIGN KEY constraint "FK_OrderLine_Product".
```

Запрос использует `OrderID = 1`. Если такого заказа нет, сначала нужно посмотреть реальные идентификаторы:

```sql
SELECT OrderID FROM lab6.Orders;
```

Затем подставить существующий `OrderID` в запрос проверки.

**Проверка 3. Добавление клиента с уже существующим Email**

```sql
USE Lab6_DDL;
GO

INSERT INTO lab6.Customer (CustomerID, Name, City, Email)
VALUES (99, N'Тестовый клиент', N'Москва', N'ivan@example.com');
GO
```

Ожидаемый результат: SQL Server отклоняет добавление клиента из-за ограничения уникальности `UQ_Customer_Email`, поскольку адрес `ivan@example.com` уже принадлежит другому клиенту.

Пример сообщения об ошибке:

```text
Violation of UNIQUE KEY constraint 'UQ_Customer_Email'.
```

**Проверка 4. Добавление второго клиента без Email**

```sql
USE Lab6_DDL;
GO

INSERT INTO lab6.Customer (CustomerID, Name, City, Email)
VALUES (100, N'Клиент без почты', N'Омск', NULL);
GO
```

Ожидаемый результат: в SQL Server эта операция также должна завершиться ошибкой нарушения уникальности `UQ_Customer_Email`.

Причина заключается в том, что в SQL Server ограничение `UNIQUE` для одного столбца допускает только одно значение `NULL`. Первый клиент без электронной почты уже был добавлен, поэтому второй клиент с `Email = NULL` не проходит проверку уникальности.

Пример сообщения об ошибке:

```text
Violation of UNIQUE KEY constraint 'UQ_Customer_Email'.
```

**Вывод по проверке ограничений**

- Ограничение `CHECK` не позволяет добавлять товары с отрицательной ценой.
- Ограничения внешних ключей не позволяют добавлять позиции заказов, ссылающиеся на несуществующие товары или заказы.
- Ограничение `UNIQUE` предотвращает повторение адресов электронной почты.
- В SQL Server уникальное ограничение на один столбец также ограничивает количество значений `NULL` одним. Если требуется разрешить нескольким клиентам не указывать электронную почту, вместо обычного `UNIQUE` можно использовать уникальный фильтрованный индекс, исключающий строки с `Email IS NULL`.

*Примечание:* приведённые сообщения — примеры формулировок SQL Server. При оформлении отчёта желательно сохранить фактические сообщения из вкладки `Messages`, поскольку сервер может выводить дополнительные строки с номером ошибки и указанием таблицы.

## Задача 2. Изменение структуры таблиц с помощью ALTER

### Задание выполнено в директории `DBCourseLabs\lab06\task02`. 

### 1. Добавление нового столбца — `02.01`

В таблицу `lab6.Customer` был добавлен новый необязательный столбец `Phone` для хранения номеров телефонов клиентов.

Для изменения структуры существующей таблицы использовалась команда `ALTER TABLE`. 

Столбец имеет тип `NVARCHAR(20)`, позволяющий хранить строки Unicode длиной до 20 символов. Свойство `NULL` указывает, что заполнение номера телефона не является обязательным.

Изменение выполнено без пересоздания таблицы и потери существующих данных.

### 2. Изменение длины столбцов — `02.02`

На этом этапе структура таблицы `lab6.Customer` была изменена с помощью команды `ALTER TABLE`. Таблица не пересоздавалась, существующие данные сохранялись.

Сначала длина столбца `Phone` была увеличена с 20 до 30 символов. Столбец остался необязательным, поскольку для него было указано `NULL`.

```sql
USE Lab6_DDL;
GO

ALTER TABLE lab6.Customer
ALTER COLUMN Phone NVARCHAR(30) NULL;
GO
```

Затем длина столбца `Name` была увеличена до 150 символов без явного указания допустимости `NULL`.

```sql
USE Lab6_DDL;
GO

ALTER TABLE lab6.Customer
ALTER COLUMN Name NVARCHAR(150);
GO
```

Для проверки изменений использовался запрос к представлению `INFORMATION_SCHEMA.COLUMNS`:

```sql
SELECT
    COLUMN_NAME,
    DATA_TYPE,
    CHARACTER_MAXIMUM_LENGTH,
    IS_NULLABLE
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_SCHEMA = 'lab6'
  AND TABLE_NAME = 'Customer'
  AND COLUMN_NAME IN ('Phone', 'Name');
GO
```

В результате проверки было установлено, что при изменении столбца `Name` без указания `NOT NULL` SQL Server допускает `NULL` для этого столбца. Это демонстрирует, что при изменении структуры необходимо явно указывать требуемую допустимость пустых значений.

Чтобы вернуть столбцу `Name` исходное ограничение обязательности, была выполнена команда:

```sql
ALTER TABLE lab6.Customer
ALTER COLUMN Name NVARCHAR(150) NOT NULL;
GO
```

После восстановления ограничения столбец `Name` имеет тип `NVARCHAR(150)` и `IS_NULLABLE = NO`, а столбец `Phone` — тип `NVARCHAR(30)` и `IS_NULLABLE = YES`.

### 3. Добавление ограничения для Email — `02.03`

Для проверки корректности адресов электронной почты было добавлено ограничение `CK_Customer_Email`, требующее наличия символа `@` в значении столбца `Email`.

Сначала был добавлен клиент с некорректным адресом электронной почты:

```sql
INSERT INTO lab6.Customer
    (CustomerID, Name, City, Email)
VALUES
    (4, N'Тестовый клиент', N'Пермь', N'invalid-email');
GO
```

Затем была предпринята попытка добавить ограничение:

```sql
ALTER TABLE lab6.Customer
ADD CONSTRAINT CK_Customer_Email
CHECK (Email LIKE '%@%');
GO
```

SQL Server отклонил операцию, поскольку существующая строка не удовлетворяла условию ограничения. При обычном добавлении `CHECK` проверяются уже имеющиеся данные, поэтому сначала необходимо исправить некорректные значения.

Email был исправлен, после чего ограничение успешно добавлено:

```sql
UPDATE lab6.Customer
SET Email = N'valid4@example.com'
WHERE CustomerID = 4;
GO

ALTER TABLE lab6.Customer
ADD CONSTRAINT CK_Customer_Email
CHECK (Email LIKE '%@%');
GO
```

**Проверка `NULL`.** Ограничение `CHECK (Email LIKE '%@%')` само по себе допускает `NULL`: сравнение с `NULL` даёт `UNKNOWN`, а ограничение `CHECK` отклоняет только результат `FALSE`. При этом дополнительное ограничение `UQ_Customer_Email` может запретить ещё одно значение `NULL`, поскольку в таблице уже имеется клиент без email.

**Проверка `WITH NOCHECK`.** При добавлении ограничения с `WITH NOCHECK` SQL Server не проверяет существующие строки. Поэтому ограничение может быть создано, даже если таблица содержит некорректный email. При этом новые изменения продолжают проверяться, а свойство `is_not_trusted = 1` указывает, что ограничение не подтверждено для всех существующих данных.

Использовать `WITH NOCHECK` без необходимости не рекомендуется: некорректные данные могут остаться в таблице, а оптимизатор SQL Server не сможет полагаться на такое ограничение как на подтверждённое для всех строк. После исправления данных ограничение следует создать без `WITH NOCHECK`, чтобы SQL Server проверил существующие записи.

### 4. Переименование и удаление столбца — `02.04`

Сначала столбец `Phone` таблицы `lab6.Customer` был переименован в `Mobile` с помощью системной процедуры `sp_rename`:

```sql
USE Lab6_DDL;
GO

EXEC sp_rename
    'lab6.Customer.Phone',
    'Mobile',
    'COLUMN';
GO
```

При выполнении процедуры SQL Server выводит предупреждение о том, что изменение имени объекта может нарушить работу скриптов и хранимых процедур, использующих старое имя. Это связано с тем, что все зависимости от прежнего имени столбца могут не обновиться автоматически.

После проверки нового имени столбец `Mobile` был удалён командой `ALTER TABLE`:

```sql
ALTER TABLE lab6.Customer
DROP COLUMN Mobile;
GO
```

В результате столбец `Mobile` удалён из таблицы. Остальные столбцы и данные таблицы сохранены.

## Задача 4. Сравнение DELETE и TRUNCATE TABLE — `task04`

Для изучения способов удаления данных была создана таблица `lab6.AuditLog`, содержащая первичный ключ `LogID` и текстовое поле `Message` длиной до 100 символов.

```sql
USE Lab6_DDL;
GO

CREATE TABLE lab6.AuditLog
(
    LogID INT NOT NULL,
    Message NVARCHAR(100) NOT NULL,

    CONSTRAINT PK_AuditLog
        PRIMARY KEY (LogID)
);
GO
```

В таблицу были добавлены три тестовые записи:

```sql
INSERT INTO lab6.AuditLog (LogID, Message)
VALUES
    (1, N'Создан клиент'),
    (2, N'Добавлен товар'),
    (3, N'Создан заказ');
GO

SELECT * FROM lab6.AuditLog;
GO
```

После проверки содержимого таблицы все строки были удалены командой `DELETE`:

```sql
DELETE FROM lab6.AuditLog;
GO

SELECT * FROM lab6.AuditLog;
GO
```

В результате все три записи были удалены, но таблица `lab6.AuditLog` сохранилась. Команда `DELETE` позволяет удалять как все записи, так и отдельные строки с помощью условия `WHERE`.

Затем была предпринята попытка очистить таблицу `lab6.Orders` командой `TRUNCATE TABLE`:

```sql
TRUNCATE TABLE lab6.Orders;
GO
```

SQL Server отклонил операцию, поскольку на таблицу `lab6.Orders` ссылается внешний ключ `FK_OrderLine_Orders` из таблицы `lab6.OrderLine`. SQL Server не разрешает выполнять `TRUNCATE TABLE` для таблицы, на которую ссылается внешний ключ, даже если дочерняя таблица пуста.

Пример сообщения об ошибке:

```text
Cannot truncate table 'lab6.Orders' because it is being referenced by a FOREIGN KEY constraint.
```

**Сравнение команд `DELETE` и `TRUNCATE TABLE`:**

- `DELETE` удаляет строки и поддерживает условие `WHERE`, позволяющее выбрать конкретные записи.
- `TRUNCATE TABLE` удаляет все строки таблицы, не поддерживает `WHERE` и обычно использует меньше записей журнала транзакций.
- Обе команды сохраняют структуру таблицы.
- `TRUNCATE TABLE` нельзя использовать для таблицы, на которую ссылается внешний ключ. В рассматриваемом примере связь между `Orders` и `OrderLine` препятствует выполнению этой команды.

**Вывод:** команда `DELETE` подходит для удаления всех или отдельных строк с учётом ограничений ссылочной целостности. Команда `TRUNCATE TABLE` предназначена для быстрой очистки всей таблицы, но имеет дополнительные ограничения. При выборе способа очистки необходимо учитывать связи между таблицами и требования к сохранности данных.

## Задача 5. Получение информации о ценах на товары

В этом задании использовались подзапросы для анализа цен товаров в базе данных `AdventureWorksLT2019`. Для выполнения запросов применялись таблицы `SalesLT.Product` и `SalesLT.SalesOrderDetail`.

Основные столбцы:
- `ProductID` — идентификатор товара.
- `Name` — название товара.
- `StandardCost` — себестоимость товара.
- `ListPrice` — прейскурантная цена товара.
- `UnitPrice` — фактическая цена продажи единицы товара.

Каждый подпункт выполнен в отдельном SQL-файле в каталоге `task05`.

### 1. Товары с прейскурантной ценой выше средней цены продажи — `task05/01.sql`

Получены идентификатор, название и прейскурантная цена товаров, для которых `ListPrice` выше средней фактической цены продажи по всем строкам таблицы `SalesLT.SalesOrderDetail`.

```sql
USE AdventureWorksLT2019;
GO

SELECT
    ProductID,
    Name,
    ListPrice
FROM SalesLT.Product
WHERE ListPrice >
(
    SELECT AVG(UnitPrice)
    FROM SalesLT.SalesOrderDetail
)
ORDER BY ProductID;
GO
```

Подзапрос вычисляет среднее значение `UnitPrice` по всем строкам заказов. Внешний запрос выбирает товары, прейскурантная цена которых выше полученного среднего значения.

### 2. Товары с прейскурантной ценой от 100 долларов, проданные дешевле 100 долларов — `task05/02.sql`

Получены товары, у которых `ListPrice` не меньше 100 долларов, а фактическая цена продажи хотя бы в одной строке заказа была ниже 100 долларов.

```sql
USE AdventureWorksLT2019;
GO

SELECT
    ProductID,
    Name,
    ListPrice
FROM SalesLT.Product
WHERE ListPrice >= 100
  AND ProductID IN
  (
      SELECT ProductID
      FROM SalesLT.SalesOrderDetail
      WHERE UnitPrice < 100
  )
ORDER BY ProductID;
GO
```

Подзапрос возвращает идентификаторы товаров, которые продавались дешевле 100 долларов. Оператор `IN` позволяет выбрать из таблицы `SalesLT.Product` только товары с такими идентификаторами, удовлетворяющие условию `ListPrice >= 100`.

### 3. Себестоимость, прейскурантная цена и средняя цена продажи — `task05/03.sql`

Для каждого товара получены идентификатор, название, себестоимость, прейскурантная цена и средняя фактическая цена продажи единицы товара в столбце `AvgSellingPrice`.

```sql
USE AdventureWorksLT2019;
GO

SELECT
    p.ProductID,
    p.Name,
    p.StandardCost,
    p.ListPrice,
    (
        SELECT AVG(d.UnitPrice)
        FROM SalesLT.SalesOrderDetail AS d
        WHERE d.ProductID = p.ProductID
    ) AS AvgSellingPrice
FROM SalesLT.Product AS p
ORDER BY p.ProductID;
GO
```

В запросе используется коррелированный подзапрос: для каждого товара вычисляется среднее значение `UnitPrice` только по тем строкам `SalesOrderDetail`, которые относятся к этому товару. Если товар не продавался, значение `AvgSellingPrice` будет `NULL`.

### 4. Товары, у которых средняя цена продажи ниже себестоимости — `task05/04.sql`

Получены товары, себестоимость которых `StandardCost` выше средней фактической цены продажи `AvgSellingPrice`.

```sql
USE AdventureWorksLT2019;
GO

SELECT
    p.ProductID,
    p.Name,
    p.StandardCost,
    p.ListPrice,
    (
        SELECT AVG(d.UnitPrice)
        FROM SalesLT.SalesOrderDetail AS d
        WHERE d.ProductID = p.ProductID
    ) AS AvgSellingPrice
FROM SalesLT.Product AS p
WHERE p.StandardCost >
(
    SELECT AVG(d.UnitPrice)
    FROM SalesLT.SalesOrderDetail AS d
    WHERE d.ProductID = p.ProductID
)
ORDER BY p.ProductID;
GO
```

Запрос использует коррелированный подзапрос для вычисления средней цены продажи и сравнивает её с себестоимостью товара. В результат попадают только товары, для которых средняя цена продажи ниже себестоимости. Товары без продаж не попадают в результат, поскольку сравнение с `NULL` не даёт истинного условия.

## Задача 6. Получение информации о клиенте

В этом задании использовалась пользовательская табличная функция `dbo.ufnGetCustomerInformation` для получения сведений о клиентах из базы данных `AdventureWorksLT2019`.

Для выполнения задания применялись таблицы:
- `SalesLT.SalesOrderHeader` — информация о заказах.
- `SalesLT.CustomerAddress` — связь клиентов с адресами.
- `SalesLT.Address` — адреса клиентов.

Для получения имени и фамилии клиента использовалась функция `dbo.ufnGetCustomerInformation`, вызываемая с идентификатором клиента.

Каждый подпункт выполнен в отдельном SQL-файле в каталоге `task06`.

### 1. Информация о клиентах для всех заказов — `task06/01.sql`

Получены идентификатор заказа, идентификатор клиента, имя, фамилия и общая сумма заказа (`TotalDue`). Результаты отсортированы по `SalesOrderID`.

```sql
USE AdventureWorksLT2019;
GO

SELECT
    soh.SalesOrderID,
    soh.CustomerID,
    ci.FirstName,
    ci.LastName,
    soh.TotalDue
FROM SalesLT.SalesOrderHeader AS soh
CROSS APPLY dbo.ufnGetCustomerInformation(soh.CustomerID) AS ci
ORDER BY soh.SalesOrderID;
GO
```

В запросе используется `CROSS APPLY`, который вызывает табличную функцию для каждого заказа, передавая ей `CustomerID`. Из результата функции выбираются имя и фамилия клиента. Общая сумма заказа берётся из `SalesLT.SalesOrderHeader`.

### 2. Информация об адресе клиента — `task06/02.sql`

Получены идентификатор клиента, имя, фамилия, первая строка адреса (`AddressLine1`) и город (`City`). Результаты отсортированы по `CustomerID`.

```sql
USE AdventureWorksLT2019;
GO

SELECT
    ca.CustomerID,
    ci.FirstName,
    ci.LastName,
    a.AddressLine1,
    a.City
FROM SalesLT.CustomerAddress AS ca
JOIN SalesLT.Address AS a
    ON ca.AddressID = a.AddressID
CROSS APPLY dbo.ufnGetCustomerInformation(ca.CustomerID) AS ci
ORDER BY ca.CustomerID;
GO
```

Таблицы `SalesLT.CustomerAddress` и `SalesLT.Address` объединяются по полю `AddressID`. Затем `CROSS APPLY` используется для получения имени и фамилии клиента из пользовательской функции. Сортировка выполняется по идентификатору клиента.
